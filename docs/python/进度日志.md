## 困难与决策

- **D1 v1.1：embed/lm_head 是否常驻** —— 现象：v1.0 预算把 embed+lm_head 4GB 计为常驻，私有 RSS ≈6~7GB，与用户「更小内存」要求冲突。根因：v1.0 沿用常规「大表常驻」直觉，未利用行表访问模式。方案 A=常驻（v1.0，快但占 4GB）；方案 B=mmap 逐行流式（每步仅访问 seq_len×4KB 行，热行由 OS 页缓存承接，私有占用≈0）。**选定 B**：CPU 场景逐行 gather 的额外延迟被页缓存命中吸收，且与 R2 零驻留理念一致；已写入 §2.1 预算表与 R9 验收（psutil 实测 ≤2.5GB）。
- **D4 v1.3：dense 层流式的触发与模式取舍** —— 现象：用户要求「内存放不下整个 dense 模型时采用层流式」。与 v1.2 既有设计（静态权重靠 OS 页缓存承接）的关系需明确。根因：页缓存是共享/可淘汰/无界策略，内存极紧时大 dense 模型会 thrash；流式 WeightRing 是有界、显式、可预算的私有策略，与 R2 专家 ring 同构。方案 A=只靠页缓存（v1.2 现状，实现最省）；方案 B=auto 双模式：静态权重 ≤ 余量 50% 走页缓存（默认、快），> 50% 自动切 WeightRing 流式（有界、稳）。**选定 B**：阈值 50% 取简单可预期（不引入动态调参）；两模式同接口（generic 组装器静态权重读取全走 manager），数值逐 token 一致（验收断言）；`weight_streaming=on/off` 手动覆盖；流式模式定位「内存可行性优先」——dense 70B BF16 每步读 140GB，启动报告打印实测盘速→预计 token/s，不承诺快（K11）。
- **D3 v1.2：transformers 是否可进运行时** —— 现象：L1 兜底层需要 transformers 运行时支持长尾架构，与 v1.0「transformers 仅参考不可运行时」的既定边界冲突。根因：R8 要求 434 架构全覆盖，纯自研积木无法在不失控的工期内容纳全部 config 变体；而 vLLM 自身就有 transformers 后端兜底层（`_TRANSFORMERS_BACKEND_MODELS`，10 条显式条目 + 机制上支持更多），说明「自研快速路径 + 上游库兜底」是业界标准分层。方案 A=全部自研（工期爆炸，K9 风险不可控）；方案 B=仅 L1 层用 transformers，L0 主路径零依赖（Ornith 及重点架构全自研，三大机制只在 L0 承诺）。**选定 B**：transformers 运行时使用严格限定在 L1 层架构，启动报告与 `/metrics` 显式标注 tier；L0 路径（含 Ornith 主测）运行时不 import transformers（仅测试对拍时 import）。
